# Decisions

Agents: if something is not covered here, take the simplest option, append a new numbered entry, continue.

## Stack choices

1. Package manager: pnpm workspaces. `.npmrc` contains `node-linker=hoisted` so React Native/Metro resolves packages inside the monorepo.
2. Mobile UI: NativeWind v4 with our own components (not React Native Paper). Paper gives a Material look, which conflicts with DESIGN.md.
3. Mobile server state: TanStack Query. Client state: Zustand (session, UI, form drafts only).
4. Validation: zod, schemas in `packages/shared`, used by API pipe and mobile forms.
5. JWT verification: `jose`. JWKS or HS256 secret depending on the Supabase project; fail closed.
6. API tests: Jest + Supertest. Mobile tests: Jest + React Native Testing Library.
7. Rate limiting: `@nestjs/throttler`.
8. Icons: Phosphor (`phosphor-react-native`) or Lucide, one set only.
9. Fonts: Archivo Narrow (display) + Public Sans (text).
10. Environments: Supabase `dev`, `test`, `prod`. Solo developer uses cloud projects, not local Docker, unless Docker is already comfortable.

## Gaps in the spec, and the answers

11. Prisma bypasses RLS because the API connects as a privileged role. API authorization is the primary control. RLS is defence in depth for any direct client access. The mobile app never reads tables directly.
12. Submission lifecycle: `draft` (editable) to `submitted` (still editable while cycle is `submission_open`) to `locked` (frozen). A member can lock their own submitted submission. Finishing the group review locks all remaining submitted ones. Revisions after lock are not implemented in M1; the API returns `SUBMISSION_LOCKED`. A revision workflow (new submission version) is a later decision, not an in-place edit.
13. Visibility during review (spec invariant 4 was undefined): from `group_review` onward, members see other members' goal fields (title, description, category, priority, estimated hours, deadline, success criteria, dependencies) for `submitted`/`locked` submissions. They never see availability, constraints or drafts.
14. Extra endpoints added: `PUT/GET /me`, `GET /groups`, `GET /cycles/:id/submission`, `GET /cycles/:id/submissions`, `GET /cycles/:id/review`, `GET /reviews/:id/comments`, `POST /cycles/:id/advance`, `POST /reviews/:id/complete`. Needed for the acceptance test.
15. One review per cycle: `UNIQUE (group_reviews.cycle_id)`.
16. Added columns: `monthly_submissions.locked_at`, `submission_goals.position`.
17. Group member cap: 12.
18. Profile creation: explicit `PUT /me` during onboarding (no DB trigger on `auth.users`). All other routes return 403 `PROFILE_REQUIRED` until it exists.
19. Cycle transitions in M1 are manual (`advance`) with the conditions in API.md. Automatic deadline transitions arrive with BullMQ in M4.
20. Non-members always receive 404, not 403, for group-scoped resources.
21. Statuses are lowercase strings in the database and TypeScript; SPEC diagram's uppercase is display only.
22. A member can comment on their own goals (self-notes are allowed). Review comments are immutable in M1 (no edit/delete).
23. Invite code format: 8 chars from `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`.
24. Redis/BullMQ is not provisioned until M4; Milestone 1 has no background jobs.
25. `profiles.id` stores `auth.users.id` directly as UUID but does not define a cross-schema foreign key constraint in Postgres, preventing Prisma P4002/P3006 multi-schema migration conflicts with Supabase's managed `auth` schema.
26. Remote PgBouncer connections: use single-query nested creates (e.g. creating group + initial owner member, creating submission + goals) to avoid transaction timeouts over high-latency connections. Multi-statement interactive transactions specify `{ maxWait: 15000, timeout: 30000 }`.
27. Added `@nestjs/swagger` in `apps/api` (non-production only) per P08 Task 5 to generate and inspect OpenAPI specifications (`apps/api/openapi.json`).
28. Mobile design system: All hex colors reside strictly in `apps/mobile/theme/tokens.ts`. Tailwind configuration dynamically loads tokens via `load-tokens.cjs` to enforce single-source-of-truth. Enforced by automated test `apps/mobile/theme/__tests__/no-hex-outside-tokens.test.ts`.
29. Mobile MonthStrip cell sizing: On standard 360dp-wide screens (320dp container), cells are computed dynamically (8dp wide with 2dp gaps for 31 days) fitting cleanly without horizontal scrolling (`requiresScroll = false`). Horizontal scrolling is enabled only if cells would be under 8dp.
30. Mobile session storage: Session persistence uses an encrypted-AsyncStorage pattern with `aes-js` (CTR mode with counter). A 256-bit AES key is generated and stored in Expo SecureStore (bypassing the 2048-byte Android SecureStore limit), while the encrypted ciphertext is stored in AsyncStorage.
31. Web preview support: For visual inspection in web browsers, `react-native-web` and `@expo/metro-runtime` are supported. Metro resolver handles `.js` extensions on relative imports in monorepo packages (`@mp/shared`) during bundling. Static export (`expo export --platform web`) is served via local HTTP server for testing.
32. AI provider selection: `LlmClient` interface abstracts LLM calls. In testing and offline dev, `FakeLlmClient` provides deterministic fixtures. When `AI_PROVIDER=gemini` or `AI_PROVIDER=openai`, API keys (`AI_API_KEY`) and models (`AI_MODEL`) exist only on the server, never exposed in client bundles or logged.
33. Excluded members in planning: Only members with `locked` submissions have plan versions generated during `planning`. Members with `draft` or `none` submission status are excluded from automated planning and do not block cycle progression.
34. Plan versioning & rate limits: Plan generation starts at version 1 (`initial`). Plan regenerations with feedback notes increment `version_number` with a hard limit of 3 generations per cycle per member. Earlier unapproved versions remain immutable for auditability.
35. Baseline plan immutability: First approval of a plan version atomically sets `is_baseline = true` and `approval_status = 'approved'`. Once baseline, the plan snapshot is immutable.
36. AI plan review UI: Follows DESIGN.md strictly (no chat bubbles). Plain row structure for questions and answers with high-contrast badge "Proposed by AI" on all unapproved plans.
37. Pure Scheduler package (`packages/scheduler`): A standalone, pure TypeScript library (`@mp/scheduler`) with no dependencies on NestJS or database ORMs. Solves task assignment over available slots with greedy Earliest Deadline First (EDF) + priority weights, hard constraint guarantees (no overlap, deadline satisfaction, dependency ordering, daily capacity), and full accounting of unscheduled tasks with explicit trade-off explanations. Verified with property-based testing via `fast-check`.
38. Timezone and calendar calculation (`packages/scheduler/src/calendar.ts`): Pure functions for month duration with leap-year support, local day-of-week mapping in IANA timezones, dated exception overrides, bidirectional local slot to UTC conversion, and day length detection across DST transitions (23h spring forward, 25h fall back) with capacity clamping.
39. Pipeline scheduler integration (`PlansService.generatePlan`): Chunks milestones into sequential daily tasks, schedules against member availability using `@mp/scheduler`, maps tradeoffs/conflicts to plan snapshot feasibility, and transactionally persists both milestone and daily task `plan_items`.
40. Mobile Weekly & Daily Planner Views: Integrates `MonthStrip` daily scheduled load gauges and active load markers, and expands weekly cards to show scheduled daily tasks with date badges, duration formatting, and zero hex literals outside `theme/tokens.ts`.
41. BullMQ & Redis infrastructure (`src/jobs/`): Redis connection uses `REDIS_URL` when provided. When `REDIS_URL` is omitted or in test environments, `JobsService` provides an in-memory queue provider supporting job addition, delayed jobs, and worker registration without requiring an external Redis daemon or Lua engine. Queues: `cycles` (for transition jobs) and `reminders` (for notification jobs). Non-production route `GET /admin/queues` reports real-time queue statuses behind `JwtAuthGuard`.
42. Task Materialization (`PlansService.approvePlan`): Upon promoting a plan version to baseline (`isBaseline = true`), daily task items (`itemType === 'daily_task'`) are materialized transactionally into the `tasks` table with links to `cycleId`, `userId`, `goalId`, and `planItemId`. Materialization checks for existing tasks by `planItemId` to maintain strict idempotency.
43. Task Execution API & Immutable Logs (`src/tasks/`): Provides `GET /tasks` (scoped strictly to user with optional cycle, date, status filters), `GET /tasks/:id` with logs, and `POST /tasks/:id/log`. Supports actions `start`, `pause`, `complete` (accumulates actual minutes, stamps `completedAt`), and `postpone` (updates scheduled date). Requires/accepts `Idempotency-Key` header stored in `task_logs.metadata`, returning the prior log on duplicate delivery. Database trigger `trg_task_logs_immutable` enforces append-only immutability.
44. Reminders & Push Tokens (`src/jobs/reminders.worker.ts`, `src/users/`): Added endpoints `PUT /me/push-token`, `GET /me/push-token`, `PUT /me/notification-preferences`, and `GET /me/notification-preferences`. Push tokens and preferences are associated with the authenticated profile. Daily task summary BullMQ jobs calculate next delivery delay against the member's IANA timezone using `@mp/scheduler` calendar conversions. Lockscreen notification bodies strictly use generic wording ("You have N tasks scheduled today") and never reveal private goal text.
45. Automatic Cycle Transitions Worker (`src/jobs/cycle-transitions.worker.ts`): Registered worker for queue `cycles` executing deadline sweeps against injected `Clock`: advances `submission_open` -> `group_review` on submission deadline (creating review row), advances `group_review` -> `planning` on review deadline (atomically locking submitted submissions and leaving drafts untouched), advances `planning` -> `execution` once all participating baseline plans are approved, and advances `execution` -> `completed` when the cycle month has elapsed UTC. Operates autonomously without blocking on missing members.
46. Mobile Today Execution View & Stopwatch Controls (`apps/mobile/app/(tabs)/index.tsx`): Integrates daily task execution directly into the Today home tab during active cycles. Displays scheduled tasks for the current calendar date (`useTasks({ date: today })`), live task status squares (`pending`, `in_progress`, `completed`, `postponed`, `paused`), and quick action buttons (`Start`, `Pause`, `Done`). Tapping a task opens `TaskActionSheet` featuring a live stopwatch timer for tracking elapsed time, custom completion minute and accomplishment note logging, and target date postponement. The `MonthStrip` visualizes daily completion ratios (`completed / total`) for the active cycle month. All UI adheres to the design token system with zero hardcoded hex values.
47. Mid-Month Reoptimization & Remaining-Work Calculation (`packages/scheduler/src/remaining-work.ts`): Reoptimization never mutates or drops completed tasks, their logs, or baseline plan items (three-record principle). A pure function `calculateRemainingWork` takes the current evaluation date (`today`), remaining availability, and current task execution states. It isolates completed work, calculates slipped tasks (uncompleted tasks with scheduled dates < today) and future tasks, maps uncompleted work to candidate tasks, and evaluates remaining capacity versus demand. Slipped tasks are preserved with overdue duration metrics to guide rescheduling priority.
48. Cycle Reoptimization Endpoint & Plain Version Diff (`POST /cycles/:id/reoptimize`): Allowed only in the `execution` phase (`plan.reoptimize`). Requires an approved baseline plan for the member. Computes remaining work from `today` through cycle end date, reschedules uncompleted tasks with the constraint-based engine into remaining availability, and saves a new `plan_versions` record (`versionType: 'reoptimized'`, `approvalStatus: 'pending'`, `isBaseline: false`, incremented `versionNumber`). Computes an immutable `diff` (moved tasks, removed tasks, summary) comparing against current task dates. The baseline version remains frozen and active `tasks` rows are not altered until the reoptimized plan is approved.
49. Reoptimized Plan Approval & Future Task Sync (`PlansService.approvePlan`): When approving a `reoptimized` plan version in `execution`: sets `approvalStatus = 'approved'`, `isBaseline = false`. Syncs future execution tasks (reschedules uncompleted matching tasks, marks dropped tasks `cancelled`, materializes new daily tasks) while completed tasks and append-only `task_logs` are preserved 100% untouched.

50. Mobile Plan Version History & Reoptimization UI (`apps/mobile/components/plans/`): Added `GET /cycles/:id/plan-versions` returning all plan versions for the calling member ordered by version number descending. Added `PlanVersionSheet` allowing members to inspect historical and reoptimized plan versions, preview structured `PlanDiff` (moved, added, removed tasks, and net day shifts), and approve pending reoptimized versions. Added `ReoptimizeSheet` with 10-char validated reason input triggering `POST /cycles/:id/reoptimize`. All components adhere strictly to the dark token system with zero raw hex literals.
51. Pure Metrics Calculator for Cycle Reports (`packages/scheduler/src/metrics.ts`, `@mp/shared`): Implemented deterministic functions for report generation: `calculateGoalAchievement` with partial-credit evaluation across success criteria (checklist, metric target, binary) or task execution fallback; priority-weighted achievement rate (`calculateWeightedAchievement`); task execution count metrics (`calculateTaskExecutionCounts`); estimate accuracy & variance (`calculateEstimateAccuracy`); consistency and active days ratio (`calculateConsistency`); dual-plan adherence comparing baseline vs current reoptimized plan (`calculatePlanComparison`); and composite `calculateCycleMetrics`. Every metric result carries its calculation inputs and human-readable formula so mobile reports can display self-explaining math derivations.
52. Individual Monthly Report Generation & Evidence-Backed AI Insights (`src/reports/`): Added endpoints `GET /cycles/:id/reports/me` and `POST /cycles/:id/reports/me/regenerate` with `ReportsService`. Reports are allowed during `execution` and `completed` phases (`report.read`, `report.generate`). Metrics are computed deterministically via `@mp/scheduler` (`calculateCycleMetrics`). AI insights generated via `LlmClient` are validated against `reportInsightSchema` requiring citations for metric IDs (`weighted_achievement`, `task_execution`, `estimate_accuracy`, `consistency`, `plan_comparison`), strictly barring ungrounded psychological claims about motives. Reports are stored once in `monthly_reports` (`report_type: 'individual'`) and never regenerated silently, requiring an explicit regeneration note.
53. Group Report Aggregation & Granular Privacy (`src/reports/`, `GET /cycles/:id/reports/group`, `PUT /cycles/:id/reports/sharing`): Aggregates group averages over shared non-null metrics only (weighted achievement, task execution totals, estimate accuracy, consistency). Unshared metrics/goals remain strictly null / empty arrays in member summaries, respecting each member's granular sharing settings. Enforces the database invariant `report_type = 'group' AND user_id IS NULL` when persisting group monthly reports.
54. Mobile Reports & Retrospectives View (`apps/mobile/app/cycles/[id]/report.tsx`, `apps/mobile/components/reports/`): Implemented tabbed individual and group retrospective views accessible during execution and completed cycle phases. Individual tab features expandable calculation derivations showing raw inputs and formula strings, dark design token SVG progress gauges (`colors.signal`, `colors.flare`, `colors.oxblood`, `colors.wash`), dual-plan baseline vs reoptimized comparison, and evidence-backed AI insights citing metric IDs. Group tab visualizes group-level averages while respecting granular member privacy settings (masking unshared metrics as 'Private' and omitting unshared goal titles). Includes `SharingSheet` for live privacy configuration and `RegenerateSheet` requiring an audit reason note.
55. XP Ledger & Gamification Engine (`packages/shared/src/gamification/xp.ts`, `apps/api/src/xp/`, `GET /me/xp`): Implemented backend-only append-only XP rewards. XP is awarded upon completing a daily task with an immutable idempotency key (`${taskId}:task_completed:1`), calculating base 25 XP plus 1 XP per 5 minutes of estimated work (capped at +25 XP bonus). Level progression is governed by a pure deterministic quadratic threshold curve `50 * (L - 1) * L` (Level 1 at 0 XP, Level 2 at 100 XP, Level 3 at 300 XP, etc.). Levels and progress are derived strictly from the aggregate sum of `xp_transactions` and are never stored as mutable counters in database columns.
56. Streaks & Achievements Gamification Engine (`packages/shared/src/gamification/`, `apps/api/src/xp/`, `GET /me/gamification`, `apps/mobile/app/(tabs)/you.tsx`): Streaks and achievements are pure deterministic projections evaluated from actual completed task dates against the member's IANA timezone. Unlocked achievements award one-off ledger rows idempotently (`achievement:${id}:1`). Displayed on the mobile "You" tab as secondary, compact rows conforming to `DESIGN.md` with level progress bar, flame streak tracker, and achievement badges adhering to dark design tokens.
57. Offline Sync Architecture & Conflict Policies (`docs/SYNC.md`): Daily task execution is local-first (`task_logs`, `tasks` cache) while planning, review, and reporting remain strictly online and server-authoritative. Task logs are zero-conflict append-only events deduplicated by deterministic idempotency keys (`${taskId}:${action}:${clientUUID}`). Task status projections follow last-writer-wins ordered by server transaction timestamps. Local mutations queue in a mobile SQLite outbox flushed via `POST /sync/push` with exponential backoff and network event triggers, and refreshed via `GET /sync/pull?since=` delta queries.
58. SQLite Outbox & Offline Sync Protocol (`apps/api/src/sync/`, `apps/mobile/services/sync/`, `POST /sync/push`, `GET /sync/pull`): Implemented local-first task execution synchronization. The mobile app queues offline task actions (`start`, `pause`, `complete`, `postpone`) with deterministic client idempotency keys into a local SQLite/AsyncStorage outbox while applying optimistic local status projections. The server endpoint `POST /sync/push` processes action batches idempotently via `TasksService`, updating task statuses and awarding completion XP atomically without duplicates upon replaying. The endpoint `GET /sync/pull?since=` returns delta queries with updated tasks, active cycle status, and user XP.
59. Month-over-Month Advanced Analytics (`packages/shared/src/analytics/`, `apps/api/src/analytics/`, `GET /me/analytics/trends`, `TrendsCard`): Computes longitudinal trends (estimation accuracy, consistency, weighted achievement, category success rates) strictly derived from historical immutable `monthly_reports` (`report_type: 'individual'`) from completed cycles. When fewer than 2 completed cycles exist, returns `status: 'insufficient_data'`. Evidence-backed AI observations strictly cite trend metric keys (`accuracy_trend`, `consistency_trend`, `achievement_trend`, `category_breakdown`) without ungrounded psychological claims. Mobile `TrendsCard` displays progression metrics and cycle history adhering to dark design tokens with zero raw hex literals.
